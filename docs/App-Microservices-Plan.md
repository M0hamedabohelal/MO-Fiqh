# خطة تحويل «يَسِّر» إلى تطبيق جوال بمعمارية خدمات مصغّرة

> مرجع مُقاس من الريبو الحالي (main @ c484b85) في 26 أكتوبر 2026.
> كل رقم في هذا المستند مأخوذ من الملفات نفسها، لا من تقدير.

---

## 0. الحكم أولًا — قبل أي مرحلة

**التطبيق (App):** نعم، ومكسبه كبير. استخدم **Capacitor** — نحو 90% من الكود الحالي يعمل كما هو
داخل WebView حديث. لا إعادة كتابة.

**الخدمات المصغّرة (Microservices):** هنا الخطر. المشروع فرد واحد (solo)، ولا يوجد فيه
سيرفر واحد اليوم — كل الوصول إلى Firestore مباشر من المتصفح عبر `src/firebase/services.ts`.
تقسيم هذا إلى عشر خدمات هو **تضاعف تكلفة صيانة بلا مقابل**، وسيُنتج نظامًا أسوأ من الحالي:
زمن استجابة أعلى، وأعطال جزئية جديدة، وثلاثة أسطح نشر بدل واحد.

النسخة التي **تنجح** وتلبّي طلبك في الوقت نفسه:

| نعم | لا |
|---|---|
| ٤ خدمات كحد أقصى، ملكية مجموعات واضحة، نشر مستقل | ١٢ خدمة، Kubernetes، Kafka، Service Mesh |
| القراءة تبقى مباشرة على Firestore (`onSnapshot`) | تمرير القراءة عبر HTTP (يقتل العمل دون اتصال) |
| كتابة + تجميع + أسرار عبر الخدمات | قاعدة بيانات لكل خدمة (DB-per-service) |
| Cloud Run (أو Functions v2) تدفع عند الاستخدام | خوادم دائمة (احسب: ٧×٢٤ مقابل ~$0) |

السبب الجوهري: الحد الحقيقي للخدمة هنا ليس «طبقة تقنية» بل **ملكية بيانات** و**حدود نشر**.
المشروع يملك هذه الحدود جاهزة بالفعل داخل `services.ts` (انظر §3)، فنستخرجها لا نخترعها.

## 2. القرارات الحاكمة

**D1 — الغلاف: Capacitor لا إعادة كتابة ولا React Native.**
`bootstrap.rtl` + framer-motion + تنسيقات WebView مدعومة. React Native سيعني إعادة كتابة
10,890 سطرًا من مكوّنات DOM (تظليل، طباعة، تصدير صورة) مقابل مكسب أداء هامشي على محتوى نصي.
الإصدار الحالي: Capacitor **8.5.3** (٩ ما زال alpha وسيغيّر iOS إلى SPM — لا تبنِ عليه الآن).
الأندرويد مطلوب `targetSdk 36` (Android 16) لكل تطبيق جديد منذ 31 أغسطس 2026.

**D2 — القراءة تبقى مباشرة، والكتابة تمرّ بالخدمات (CQRS خفيف).**
`subscribeToLessons` (`services.ts:31`) يمنحك: تحديثًا لحظيًا، كاش Firestore يعمل دون اتصال
(`contentCache.ts`)، صفر باردة، وصفر تكلفة سيرفر. تمريره عبر HTTP يعني: انتظار cold start،
فقدان الاشتراك اللحظي، وكسر مسار `resolveContentSource` (`contentSource.ts:16`).
المسار المباشر **عام ومقروء فقط** بقواعد الأمان؛ لا سرّ فيه.

**D3 — أربع خدمات، كل واحدة تملك مجموعاتها.**

**D4 — Firestore مشترك + ملكية، لا قاعدة لكل خدمة.**
قاعدة لكل خدمة تعني ٤ نسخ احتياطية، ٤ مخططات، ومعاملات موزّعة — على مشروع فردي هذا انتحار
تشغيلي. الفصل يُفرض بـ **قواعد الأمان**: لا خدمة تكتب في مجموعات غيرها (تُفرَض بحساب خدمة
مخصّص لكل خدمة، لا بمفتاح أدمن واحد للجميع).

**D5 — الخدمات تُكتب بـ TypeScript على Cloud Run، بنفس `tsconfig` وأنواع مشتركة.**
لغة ثانية (Go/Python) = سياقان في رأسك. الأنواع المشتركة تُستخرج من `src/types.ts` إلى
حزمة `packages/contracts` يستخدمها العميل والخدمة معًا — العقد لا ينحرف.

## 4. عقود الـ API

قواعد ملزمة لكل الخدمات:

- **الإصدار في المسار**: `/v1/...` — لا كسر للعميل القديم (تطبيق مثبّت على جهاز لا يُحدَّث فورًا).
- **المصادقة**: `Authorization: Bearer <ID token>`؛ الخدمة تتحقق بـ
  `admin.auth().verifyIdToken()` — لا تثق بأي `uid` في الجسم.
- **الكتابة المتكرّرة آمنة**: `Idempotency-Key` إلزامي على `POST`.
- **المكتبة**: `PUT /v1/library/{uid}` مع `If-Match: <revision>` — يمنع «آخر من يكتب يفوز»
  الموجود اليوم في `setDoc` (`useLibrarySync.ts:343`)، وهو سبب محتمل لفقدان تظليل بين جهازين.
- **غلاف خطأ واحد**: `{ "error": { "code": "CONTENT_NOT_FOUND", "message": "…", "requestId": "…" } }`.
- **حدود**: جسم ≤ 1MB (المحتوى الكبير عبر media)، مهلة 10 ثوانٍ، `Retry-After` عند 429.

```http
PUT /v1/library/abc123
Authorization: Bearer <idToken>
If-Match: "rev-42"
Content-Type: application/json

{ "bookmarks": [1,7], "highlights": [], "readLessons": [3],
  "stopMarks": {}, "theme": "dark", "revision": 43 }
```
```json
201 { "revision": 43, "merged": true, "tombstonesPruned": 0 }
409 { "error": { "code": "REVISION_CONFLICT", "message": "…", "requestId": "r-8f2" } }
```

## 5. البنية التحتية

**الترتيب المقترح للمستودع** (monorepo بنفس `npm`، بلا Turborepo في البداية):

```
services/
  shared/        # verifyToken, errorEnvelope, firestoreAdmin, logger
  content/       src/index.ts   (+ Dockerfile)
  library/
  engagement/
  media/
packages/contracts/   # أنواع مشتركة مستخرجة من src/types.ts
src/                  # الواجهة كما هي + طبقة apiClient رقيقة
```

**Cloud Run أم Functions v2؟**

| | Cloud Run | Functions v2 |
|---|---|---|
| التحكم/الصور | Docker كامل، تبعيات حرة | مقيّد |
| الاختبار محليًا | `docker run` = مطابق للإنتاج | محاكي |
| التكلفة | مجاني حتى حد سخي، `min-instances=0` | مشابه |
| الأنسب لك | **نعم** (اختبار محلي مطابق، D5) | بديل أبسط لو أردت السرعة |

**ثلاث نقاط تُنسى عادة وتكسر المشروع:**

1. **CSP** — `firebase.json` يقيّد `connect-src` بقائمة مغلقة. أي نطاق API جديد **يُحجب
   صامتًا** في المتصفح. لا بد من إضافة أصل الـ API (والنطاق المحلي للتطوير) وإلا كل شيء
   «يعمل» في الاختبار ويفشل في الإنتاج.
2. **CORS** — الخدمات تسمح بأصل الويب فقط؛ Capacitor يشغّل من `capacitor://localhost` أو
   `http://localhost`، فالقائمة تحتاج هذه الأصول صراحة.
3. **قواعد الأمان** — بعد نقل الكتابة للخدمات، **أغلقها في القواعد**:
   `allow write: if false` على `lessons` من العميل، مع إبقاء القراءة عامة. وإلا فتحنا مسارين
   للكتابة وانتقل الخطر من مكانه.
4. **الأسرار** — `CLOUDINARY_API_SECRET` في Secret Manager فقط، ويُقرأ بخدمة media. الرفع
   غير الموقّع الحالي يسمح لأي زائر باستهلاك حصّتك.

## 6. مراحل التنفيذ

كل مرحلة تُشحن مستقلة وتُختبر قبل التالية. لا «انطلاق كبير».

### المرحلة ١ — غلاف Capacitor (٣–٥ أيام)
- `npm i @capacitor/core @capacitor/cli` + `npx cap init` + منصّة أندرويد.
- `vite.config.js`: `base: './'` أو ضبط `server` حسب الحاجة، والتأكد من `hashFromCleanPath`
  (`main.tsx`) داخل `file://`/`capacitor://`.
- إعدادات: `capacitor.config.ts` (appId, splash, status bar RTL)، `targetSdk 36`.
- **الخروج:** APK مثبّت على جهاز حقيقي يفتح، يقرأ دون اتصال، ويحفظ التظليل بعد إعادة التشغيل.

### المرحلة ٢ — تكييف الجوال (٣–٤ أيام)
- زر الرجوع الأندرويدي ↔ `useHashRoute` (الآن الرجوع يخرج من التطبيق بدل الرجوع للمسائل).
- `safe-area-inset` للشريط السفلي `MobileBottomNav`، والكيبورد في البحث.
- الطباعة/تصدير PDF على أندرويد: `printExport.ts` يحتاج WebView print أو مشاركة ملف.
- **الخروج:** لا فراغات، لا قصّ، الرجوع منطقي في ١٠٠% من المسارات.

### المرحلة ٣ — الدخول على الجوال (٢–٣ أيام) ⚠️ أعلى مخاطرة تقنية
- `signInWithPopup` **لا يعمل** في WebView. الحل: `@capacitor-firebase/authentication`
  (Google/Apple أصلي) ثم `signInWithCredential` في JS.
- شاشة الدخول الحالية (`LoginModal`) تعمل للبريد/كلمة المرور كما هي.
- **الخروج:** دخول Google ناجح على جهاز حقيقي + بقاء الجلسة بعد إعادة التشغيل + تسجيل خروج.

### المرحلة ٤ — طبقة العميل مقابل الـ API (٢ أيام)
- `src/api/client.ts`: `withAuth()`, `retry()`, `idempotencyKey()`.
- تحويل `useLibrarySync` لاستخدام `PUT /v1/library` (مع flag رجوع للمسار المباشر).
- **الخروج:** المكتبة تتزامن بين الويب والتطبيق؛ الفحص الآلي الحالي (`npm test`) أخضر.

### المرحلة ٥ — خدمتا content و library (أسبوع–١٠ أيام)
- استخراج المنطق من `services.ts` إلى الخدمتين + اختبارات عقد (contract tests) تشغّل نفس
  حالات `services.ts` الحالية.
- خفض صلاحية الكتابة في `firestore.rules` للعميل.
- **الخروج:** لوحة الإدارة تعمل بالكامل عبر الخدمة، والمسائل لا تُكتب من العميل إطلاقًا.

### المرحلة ٦ — engagement + media (٤–٥ أيام)
- الرفع الموقّع عبر media-svc؛ تحويل `utils/cloudinary.ts` لطلب توقيع أولًا.
- **الخروج:** لا مفتاح Cloudinary في الحزمة (`grep` على `dist/` يثبت ذلك).

### المرحلة ٧ — المتجر (٤–٦ أيام، قابلة للتوازي)
- Play Console ($25 مرة واحدة): توقيع AAB، Data safety، سياسة خصوصية، لقطات، وصف.
- خيار TWA/العرض: لو أردت نشرًا فوريًا بلا Capacitor، PWA الحالية تكفي كـ TWA — لكن بلا
  وصول للعتاد ولا دفع، و«إحساس الموقع» يبقى.
- **الخروج:** نسخة داخلية (Internal testing) على ٥ أجهزة.

**الإجمالي الواقعي: ٦–٨ أسابيع بدوام جزئي**، والأندرويد أولًا.

## 8. معايير القبول (قابلة للقياس)

1. APK على جهاز حقيقي: يفتح دون اتصال ويعرض **٨٥ مسألة** — وهو عدد Firestore الحقيقي المقاس
   بـ `npm run audit:data -- --live` اليوم، لا ٧٩ لقطة البناء ولا اللقطة القديمة.
2. `npm run typecheck && npm run lint && npm run test && npm run build` أخضر بعد كل مرحلة.
3. لا سرّ في `dist/`: `grep -r "CLOUDINARY_API_SECRET\|AIza" dist/` → لا نتائج (مفتاح
   Firebase عام بطبيعته، لكن السرّ لا).
4. الكتابة من العميل إلى `lessons` مرفوضة في القواعد: محاولة مباشرة ترجع `permission-denied`.
5. زمن فتح أول مسألة على 4G ≤ ١.٥ ثانية (قياس حقيقي، لا تقدير).
6. `docker run` لكل خدمة يبدأ محليًا؛ اختبار عقد لكل مسار `/v1` (نجاح + 401 + 409).
7. مراقبة: تنبيه واحد على الأقل لكل خدمة (نسبة أخطاء 5xx > 1%).

## 10. الخطوة الأولى (ساعتان، اليوم)

```bash
# 1) غلاف بلا أي تعديل على الكود
npm i @capacitor/core @capacitor/cli @capacitor/android
npx cap init "يَسِّر" app.yasser.fiqh --web-dir dist
npm run build && npx cap add android && npx cap sync
# 2) قياس الحقيقة: هل يفتح ويقرأ؟
npx cap open android        # أو ./gradlew assembleDebug ثم adb install
```

المخرج من هذه الساعتين يجيب على السؤال الوحيد المهم قبل ٦ أسابيع من العمل:
**هل هذا الكود يعمل داخل WebView كما هو؟** لو نعم — الخطة أعلاه صحيحة. لو لا — نعرف بالضبط
أي مكوّن يعاند، ونحن لم نغيّر سطرًا واحدًا بعد.
